# Project 8 · TCR 序列检索的倒排索引模块

给定一条查询序列和编辑距离阈值 `d`，这个模块先从参考库中筛出可能匹配的序列，再由动态规划（DP）计算准确距离。**候选 ID** 表示“还需要算距离”；**最终匹配**表示“两条完整序列的编辑距离小于或等于 `d`”。(一份核心代码，两份辅助代码，宗政在整合的时候可以选择性进行使用或部分整合)

| 文件 | 角色 | 用途 | 入口 |
| --- | --- | --- | --- |
| `inverted_index.py` | **核心代码** | 建立倒排索引，为每条查询生成候选 ID | 命令行，或在 Python 中调用 `InvertedIndex` |
| `integration_example.py` | 辅助代码（DP 对接示例） | 把候选交给指定的 DP 函数，返回最终匹配 | 在主程序中导入 `search_one` |
| `test_inverted_index.py` | 辅助代码（单元测试） | 检查候选筛选、文件读写和 DP 对接 | 运行 `unittest` |

**运行环境**　Python 3.9 或以上

## 1. inverted_index.py · 生成候选

### 先跑一个能看懂结果的例子

下面两条命令在当前目录创建两份 UTF-8 TSV 示例文件。文件名以 `demo_` 开头，重复运行会覆盖同名文件。

```sh
python -c "from pathlib import Path; Path('demo_refs.tsv').write_text('reference_id\tsequence\nR1\tCASS\nR2\tCATS\nR3\tCAYY\nR4\tYYYY\n', encoding='utf-8')"
python -c "from pathlib import Path; Path('demo_queries.tsv').write_text('query_id\tsequence\nQ1\tCASS\nQ2\tCAS\n', encoding='utf-8')"
```

运行索引，再查看输出文件。终端的第一条命令会打印一行统计摘要；每条查询的候选明细写在 `demo_candidates.jsonl` 里。

```sh
python inverted_index.py --reference demo_refs.tsv --queries demo_queries.tsv --k 2 --d 1 --output demo_candidates.jsonl
python -c "from pathlib import Path; print(Path('demo_candidates.jsonl').read_text(encoding='utf-8'))"
```

| 查询 | 输出中的 `mode` | 输出中的 `candidate_ids` | 原因 |
| --- | --- | --- | --- |
| Q1 · `CASS` | `indexed` | `["R1","R2","R3"]` | 查询可切成 `CA` 和 `SS`。前三条参考都含 `CA`，长度也合格。即使 R3 的真实距离为 2，这一步仍会保留它。 |
| Q2 · `CAS` | `fallback` | `["R1","R2","R3","R4"]` | 查询只有 3 个字符，放不下两段长度为 2 的种子。四条参考长度都是 4，与查询的长度差均为 1，因此都要交给 DP。 |

### 换成项目数据（对接倬含的数据）

把 `--reference` 和 `--queries` 换成实际 TSV 的路径即可，文件可以放在任意目录。相对路径从**当前终端所在目录**算起；路径含空格时用双引号括起来。如果数据是 ZIP，先解压，再指定里面的 TSV。

| 参数 | 含义 |
| --- | --- |
| `--reference`、`--queries` | 必填。两份文件都用制表符分列，第一行是表头。参考表须有 `reference_id`、`sequence`；查询表须有 `query_id`、`sequence`。允许额外列和不同列序。 |
| `--d` | 必填。允许的最大编辑距离，取非负整数，包含边界。插入、删除、替换一个字符各算一次编辑。 |
| `--k` | 每段种子的长度，取正整数，默认 3。适合的取值取决于查询长度和阈值，见第 5 节。 |
| `--strategy` | 查询种子的取法，可选 `spread`（默认）或 `prefix`。 |
| `--output` | 候选 JSONL 的路径。父目录须已存在；同名输出文件会被覆盖。省略时，候选写入标准输出，统计摘要写入标准错误。 |

两个 TSV 的输入规则相同：ID 非空、无首尾空白、在各自文件内唯一；序列非空，只使用 20 种标准氨基酸的大写单字母代码。同一序列可以对应不同参考 ID，这些记录会分别保留。

### 核心代码功能讲解

读这份代码可以从 `InvertedIndex` 开始。它先把参考库整理成可复用的倒排索引，再通过 `generate_candidates()` 给每条查询找出值得交给 DP 的候选 ID。下面用前面的 `CASS` 和 `CAS` 两条查询走一遍。

1. **建索引（`InvertedIndex(references, k)`）。** 取 `k=2` 时，参考序列 `R1 = CASS` 的滑动窗口依次切出 `CA`、`AS` 和 `SS`，三段对应的 ID 集合里都会加入 `R1`。这张「片段 → 参考 ID 集合」的表就是 `postings`。用集合存 ID，所以同一片段在同一条参考里出现多次也只记一次。索引还保留两张表。`references` 用 ID 查完整序列，`by_length` 用序列长度查参考 ID。即使参考序列短到切不出 k-mer，也会放进 `by_length`，让回退查询还能找到它。
2. **选查询种子（`select_seed_positions()`）。** 查询长度记作 `m`。当 `m >= k * (d + 1)` 时，代码取 `d+1` 段长为 `k`、互不重叠的种子。每次编辑最多破坏其中一段，所以编辑距离不超过 `d` 的参考序列里，至少能找到一段完整种子。插入或删除可能改变种子的位置，查表时只需要匹配它的内容。两种策略都用从 0 开始的下标。比如 `m=15`、`k=3`、`d=2` 时，`prefix` 从开头紧挨着取，起点为 0、3、6。默认的 `spread` 把种子铺开，起点为 0、6、12。查询太短时，函数返回空元组 `()`。
3. **生成候选（`generate_candidates()`）。** 代码先找出长度差不超过 `d` 的参考长度组。每次插入或删除最多改变一个字符的长度，所以长度差大于 `d` 的参考可以直接排除。
   - **正常查索引（`indexed`）。** 在 `k=2`、`d=1` 时，查询 `CASS` 用 `CA` 和 `SS` 查表。`CA` 查到 `R1`、`R2`、`R3`，`SS` 查到 `R1`。两份集合取并集，再按长度过滤，得到三个候选 `R1`、`R2`、`R3`。种子都查不到时，候选集合为空。
   - **短查询回退（`fallback`）。** 同样的参数下，`CAS` 只有 3 个字符，放不下两段长度为 2 的种子。此时直接合并所有长度合格的参考 ID。示例里的四条参考都长 4，因此全部交给 DP，验证时仍用原来的 `d=1`。
4. **读取结果（`CandidateResult`）。** 在 Python 里用 `result.candidate_ids` 取候选集合，用 `result.mode` 判断这次走的是索引还是回退。`seed_positions`、`seeds`、`posting_sizes` 分别记录种子的起点、内容和各自查到的 ID 数。`union_count` 记录倒排命中结果合并去重后的数量，尚未按长度过滤，回退时输出为 `null`。`length_eligible_count` 统计整个参考库里长度合格的 ID 数，`candidate_count` 则是过滤后写出的候选总数。
5. **从命令行跑整批查询。** `main()` 解析参数并调用 `read_sequences()`，把参考 TSV 和查询 TSV 分别读成「ID → 序列」字典。`run_search()` 建一次索引，随后对每条查询调用 `generate_candidates()`。`CandidateResult.to_dict()` 会把候选 ID 按字典序排好，每条查询写成一行 JSON。即使候选为空，也会写出该查询的结果。

## 2. integration_example.py · 把候选交给 DP

`search_one()` 处理一条查询。它生成候选，按 ID 取出完整参考序列，调用传入的 `verifier(query, reference_sequence, d)`，并把距离在阈值内的记录写入 `matches`。每条命中记录包含 `reference_id`、`sequence`、`distance` 和 `annotations`。没有注释时该字段为 `[]`，没有命中时查询仍返回 `{"query_id": ..., "matches": []}`。

下面这段可以在三个文件所在目录的 Python 交互环境中运行。它沿用第 1 节的参考表，借用测试文件中的精确距离函数来演示接口。

```python
from inverted_index import InvertedIndex, read_sequences
from integration_example import search_one
from test_inverted_index import oracle_distance

index = InvertedIndex(read_sequences("demo_refs.tsv", "reference_id"), k=2)

def demo_verifier(query, reference, d):
    return oracle_distance(query, reference)

result = search_one(index, "Q1", "CASS", d=1, verifier=demo_verifier)
print([(hit["reference_id"], hit["distance"]) for hit in result["matches"]])
```

预期输出为 `[('R1', 0), ('R2', 1)]`。这里可以看到候选和匹配的区别：R3 通过了种子筛选，但从 `CASS` 变成 `CAYY` 需要两次替换，DP 在 `d=1` 时将它排除。

## 4. 接入小组主程序

- **数据和索引。** 用 `read_sequences(path, "reference_id")` 加载参考，用 `read_sequences(path, "query_id")` 加载查询。每套参考数据、每个 `k` 建一次索引，供整批查询复用。更换 `d` 或 `strategy` 可以沿用原索引；参考数据或 `k` 变化时重建。
- **DP 接口。** 把组里的 DP 函数作为 `verifier` 传入。距离在阈值内时返回准确的非负 Python `int`（包括 0）；超限时返回 `None` 或大于 `d` 的整数。若已有函数用 `-1` 表示超限，在传入前将它转换成 `None`。只返回 `True/False` 无法提供最终结果需要的距离。
- **批量输出。** 遍历查询字典，对每条调用一次 `search_one`，将返回值逐行写成 JSONL。可选的 `annotations` 参数接收“参考 ID → 原始注释记录列表”；需要输出注释时，由主程序单独读取这些列。整合后，用同一批查询逐条核对最终匹配的 ID 和精确距离，包含零命中查询。

## 5. 关于Benchmark部分的一些思路（只是我自己的一些想法，尤其是k的选择上具体还要结合更多同类型研究看看有无更合适的行业经验或者规则）

实验要回答三个问题：能否找全阈值内的匹配？索引实际省掉了多少次 DP？把建索引的时间和内存也算进去，这笔开销在多大的参考库、多少条查询下能收回来？

### 5.1 先定对照，再定参数

| 想回答的问题 | 两组怎么跑 | 重点看什么 |
| --- | --- | --- |
| 索引能否找全匹配？ | 用基础 DP 穷举得到真值。长度差超过 `d` 的序列可直接排除。逐条查询比对真值、索引候选和 DP 验证后的结果。 | 每个真实匹配 ID 都应进入候选。最终匹配的 ID 和精确距离应逐条一致，零命中查询也要保留。 |
| 索引值不值得建？ | A 组对所有长度合格的参考做 DP；B 组先筛候选，再调用**同一个 DP**。两组用完全相同的参考库、查询和 `d`。 | 候选减少量、整批查询时间、建索引时间和峰值内存。 |
| 优化版 DP 本身快多少？ | 固定同一份候选序列对，分别交给基础 DP 和优化 DP，采用相同的阈值和输出约定。 | 先核对命中和精确距离，再比较 DP 耗时。这样能分清索引和 DP 各自带来的收益。 |

### 5.2 怎么选值得比较的 k？（我自己的想法，不一定完全合理合适）

这里的 `k` 是索引种子的长度。固定查询、参考库和阈值 `d` 后，各个 `k` 应当得到相同的最终匹配。要比较的是为找到这些匹配，各自需要做多少筛选和距离计算。

我自己的一种想法是先在相同查询上比较小、中、大三个可用的 k。 固定 d，按查询长度分组。设组内最短查询长度为 m_min，要让整组都能走索引，可选范围是 1 ≤ k ≤ K，其中 K = m_min // (d+1)。`K ≥ 3` 时取 1、中点（向下取整）和 K；只有一两个值时全部测试。若 K=0，组中最短查询在任何正整数 k 下都会回退，可将这些查询单独统计。（说白了就是在所有符合公式要求的k值里面选取用大中小三类不同典型的k进行验证和比较）

**本项目建议先看查询长度分布。** 对长度为 `m` 的查询，要放下 `d+1` 段互不重叠的种子，需要 `k ≤ ⌊m/(d+1)⌋`。例如 `m=15、d=2`，能走索引的整数只有 1 到 5，在这一长度组内可以全部比较。混合长度实验则应让每个备选 `k` 跑完同一批查询，把回退的查询也计入总耗时。

**预算有限时，优先比较会改变检索行为的相邻值。** 例如配套真实数据有 100 条查询，固定 `d=2`，当 `k` 分别为 3、4、5、6 时，能走索引的分别有 100、99、51、8 条。这里尤其值得比较 4 和 5：种子只增长一个字符，就有 48 条查询从索引转为回退。可以先看较长种子为仍走索引的查询省了多少次 DP，再看这部分节省能否抵过新增的回退开销。将整数范围三等分再取中位数也能压缩实验量，但有可能跳过这种转折点。

最终推荐哪个 `k`，看相同真值、相同查询下的整批耗时和内存。参考库反复使用时单列建库成本；一次性任务则把建库计入总时间。如果要把推荐值用于后续查询，可再用保留的一批查询确认。

### 5.3 哪些数据最容易拉开差距？

| 实验因素 | 建议做法 | 结果怎么解释 |
| --- | --- | --- |
| 参考库规模 | 在 1,000、5,000、10,000 条参考上复用同一批查询，记录各库的长度分布。大库先抽取一批查询测穷举耗时，再按查询数估算完整实验用时。 | 看参考库增大以后，建库开销、查询加速比和内存如何变化。 |
| 查询长度和编辑阈值 | 长度 8、12、18 的合成数据可分别比较 `d=0,1,2,3`。保留恰好命中阈值、刚超阈值和零命中的查询。插入、删除、替换都要覆盖，用完整 DP 核实实际距离。 | 同样允许两次编辑，对 8 位和 18 位查询意味着不同的相对差异，也会给种子留下不同的空间。 |
| 常见片段和种子位置 | 固定参考数、长度、`k` 和 `d`，比较不同 motif 比例的数据及对应 probes，再分别运行 `prefix` 和 `spread`。查看 `seeds`、`posting_sizes` 和 `union_count`。 | 某个常见片段只有实际被选为种子，才会通过它的倒排表扩大候选并集。若两种策略选到相同位置，应预期相同候选。 |

### 5.4 计时和结果怎么记？

- **区分多余候选与检索错误。** 一个真实距离超出 `d` 的 ID 进入候选，会多花一次 DP；如果它在验证后仍被输出，才计为最终假阳性。逐配置记录漏掉的真实匹配数、最终假阳性数和距离错误数，预期均为 0。
- **用实际 DP 次数衡量筛选效果。** 对整批查询求和，`1 − 总候选数 / 总长度合格数` 就是相对长度过滤穷举省掉的 DP 比例。分母为 0 时记为不适用。另记回退查询占比和每条查询候选数的中位数、95 分位数，避免少数命中常见种子的慢查询被平均值掩盖。
- **把一次性成本算清。** 分开记录建索引、生成候选、DP、整批检索及进程峰值内存，注明文件读写是否计时。由外部 Benchmark 分别测量 `InvertedIndex(...)` 的建索引耗时和 `generate_candidates(...)` 的候选生成耗时，并单独实测进程峰值内存。若索引每条查询平均省时为正，用“建索引耗时 ÷ 每条查询平均省时”可粗估需要多少条同类查询才能收回建库时间。
- **保证可复现。** 固定数据版本、查询 ID、抽样随机种子、机器和 Python 版本。各配置采用相同预热方式，交替运行待比较的方法，各测 5 次，保留原始记录，报告中位数及均值的标准误（样本标准差除以 √5）。加速比统一用“基线耗时 / 索引方案耗时”，分别列出含建库和复用索引两种结果。
